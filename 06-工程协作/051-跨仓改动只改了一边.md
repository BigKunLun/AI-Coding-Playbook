# 051. 前后端分仓，让 AI 改一个字段它只改了一边怎么办？（跨仓工作区 + 接口契约治理）

> 难度：中级
> 主题：工程协作
> 工具：Claude Code · 横向(Cursor / Copilot)
> 题型：配置题 + 流程题 + 排错题

> ⏰ 时效声明：本篇的多仓配置事实已于 **2026-08-03** 重新对照官方 [large-codebases 文档](https://code.claude.com/docs/en/large-codebases) 逐条核实。具体包括：`additionalDirectories` 永不加载对方 CLAUDE.md/rules 和 skills；`--add-dir`（含会话内 `/add-dir`）加载 skills，并且只有在设置 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` 时才加载对方 CLAUDE.md 和 rules；该环境变量对 `additionalDirectories` 无效；两者都是读写权限。参数语义随版本可能变化，请以官方为准。本篇「契约怎么选、CI 怎么卡」两节的事实性内容与外链于 **2026-07-18** 复核；其中「有 spec 让 LLM 生成代码错误率最高降 50%」为 arXiv:2602.00180 对 controlled studies 的转述（未逐一回溯原始研究），「60-70% 破坏性改动蒙混过 review」无具体研究出处，仅作方向性参考。oasdiff / Schemathesis 等工具能力以官网现行文档为准。

## TL;DR

前端一个仓、后端一个仓，让 AI 加一个「前后端都要动」的字段，它常常只改一边，或者两边字段名对不上。

根因不是模型笨。真正的问题是：决定这次改动安不安全的依赖关系，横跨两个仓。它落在任何单个仓的边界之外，也就落在 AI 的上下文窗口之外。对 AI 来说，每个仓都是一座孤岛。

下面是四点速记。

**第一，先做决策：能合并成 monorepo 就别硬扛多仓。** monorepo 指把多个项目放进同一个代码仓库。合仓后 AI 一次就能看到前后端两边。多仓协作的麻烦本质都是「AI 看不到全局」，合仓从根上消除了它（见 [#050](./050-大仓库monorepo里不迷路.md)）。只有因为团队边界、权限隔离、发布节奏而确实不能合的场景，才需要下面的手段把分散的上下文聚拢起来。

**第二，配置层：用 `additionalDirectories` 或 `--add-dir` 把相邻的仓拉进同一会话。** 这是官方支持的多仓文件访问机制。关键坑在于：`additionalDirectories` 只给文件读写权限，不会加载那个目录的 CLAUDE.md 和 skills。这一点官方有明确说明。

**第三，结构层：用一个「元仓库」当工作区根。** 元仓库是一个不含业务代码的父目录，里面只放清单文件和跨仓的 CLAUDE.md。把多个业务仓作为并列的子目录克隆进来，AI 就有了一个能看到全景的起点。

**第四，接口层：别让 AI 靠记忆对齐字段，让契约当裁判。** 把两个仓放进同一会话只解决「看得见」，解决不了「字段名对不上」。字段名一致要靠一个独立于前后端实现之外的第三方真值源，也就是契约：OpenAPI、共享类型包或 GraphQL schema。改字段先改契约，代码从契约生成或对着契约校验，再用 CI 里的 spec-diff 和契约测试当硬闸门（见「怎么做」第四步选载体、第五步上 CI 闸门）。

一句话切边界：本篇讲多仓工作区怎么搭、接口契约怎么当裁判、一次跨仓改动怎么走完并双边验证。单仓内跨包不裂开归 [#050](./050-大仓库monorepo里不迷路.md)；需求怎么写成规格归 [#021](../03-需求与规划/021-动手前要不要写PRD.md)；git 分支和 PR 怎么配 AI 归 [#052](./052-别让AI搞乱git仓库.md)。

## 为什么

### 1. 跨仓上下文天生是断的，每个仓都是一座孤岛

在单仓里，AI 能顺着 import 找到定义。跨仓时，前端仓里根本没有后端的代码，AI 对「后端那个接口长什么样」一无所知。

一次典型的翻车长这样。在 `frontend/` 里启动 Claude Code，提示词是：

```text
给用户资料加一个手机号字段，前后端都要改。
```

AI 的实际产出：

1. 在 `frontend/src/types/user.ts` 里加了 `phone: string`。
2. 在表单组件里加了输入框，提交时发 `{ phone }`。
3. 说了一句「后端也需要相应添加 phone 字段」，然后结束。

后端仓压根没被读过，更没被改过。就算你把后端目录也给了它，还有第二种翻车：前端写 `phone`，后端字段叫 `phone_number`，两边各自的类型检查都通过，联调时才发现值永远是 `undefined`。

根因是结构性的：决定一次改动安不安全的依赖关系，活在任何单个仓的边界之外，也就活在 AI 的上下文窗口之外。AI 交出一份「本地看起来正确」的代码，却打断了它根本不知道存在的下游使用方。

这不是 Claude Code 独有的问题，Cursor 和 Copilot 同样撞墙。GitHub 官方承认，background agent「在单个仓的上下文里表现最好」，多仓场景当前建议「把工作拆成针对单个仓的子任务」（[GitHub 社区讨论](https://github.com/orgs/community/discussions/186469)，官方论坛，2026）✅。社区里也有人把这个状态概括成「每个仓都是一座孤岛」，但那句话出自产品推广贴，只当形象说法看，不作为论据（社区，2026）⚠️。

所以别指望换个模型解决。这是上下文边界问题，只能靠工作区结构解决。

### 2. 决策优先：多仓的痛，一半能靠「别分仓」消掉

在堆配置之前先问一句：这几个仓非分不可吗？

如果分仓只是历史惯性，把强耦合的前后端合进 monorepo，AI 一次就能看到两边，跨包改动一把过。这是成本最低的解法（详见 [#050](./050-大仓库monorepo里不迷路.md)）。

真正需要多仓手段的，是那些因为团队边界、权限隔离、独立发布节奏而不能合的场景。别为了用工具而保留分仓，也别为了省事硬把该独立的服务塞进一个仓。

### 3. 官方给的是「文件访问」，不是「上下文合并」，这层区别是最大的坑

Claude Code 对多仓的支持很直接：用 `additionalDirectories` 设置或 `--add-dir` 标志，就能「在同一会话里读写相邻的包或另一个仓」。

但它给的只是文件读写权限，默认不会把那个目录的记忆和技能加载进来：

> `additionalDirectories` setting —— Loads CLAUDE.md and rules: **Never**；Loads skills: **Never**。
> `--add-dir` flag —— Loads CLAUDE.md and rules: **Only with the environment variable below**；Loads skills: **Yes**。
>
> 大意：`additionalDirectories` 永不加载对方的 CLAUDE.md、规则和技能；`--add-dir` 会加载技能，但只有配上下面那个环境变量才加载 CLAUDE.md 和规则。
> —— [Claude Code 文档：large-codebases](https://code.claude.com/docs/en/large-codebases)（官方，2026-07）✅

换句话说，你把后端仓用 `--add-dir` 拉进来，AI 能读能改它的文件，但后端那份 CLAUDE.md（里面写着约定、架构、命令）默认不进上下文。要让它进来，得用 `--add-dir` 并显式设置 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`。

很多人抱怨「AI 改后端不守后端规范」，根因就在这：你给了它文件，没给它那个仓的「说明书」。

### 4. 就算两个仓都看得见，字段名照样会漂——因为 AI 靠记忆对齐

把后端拉进会话，只解决了「看不见」。还有一类翻车是「看得见也对不上」。

你让 AI 给用户加 `phone`，它在后端加了校验和落库；轮到前端时，它靠上下文里的记忆去回忆后端刚才叫什么。长会话一压缩（compact），记忆就变了：后端是 `phoneNumber`，前端写成 `phone`。两边各自的类型检查都过，联调才发现值永远是 `undefined`。

指望 code review 挡住这类漂移也不现实。评审者盯的是 PR 的业务逻辑，不是「这次响应模型的改动是否和 spec 一致」，spec 和实现往往在不同目录的不同文件里，改一个不会在视觉上高亮出另一个也该改。有社区文章给了一个典型场景：开发者把响应字段从 `user_id` 改名成 `userId`，接口还能跑、单测还绿，但 OpenAPI spec 没更新；三周后依赖 `user_id` 的移动端在生产崩溃，团队花两天才追溯到这次改名（[TotalShiftLeft: API Schema Validation](https://totalshiftleft.ai/blog/api-schema-validation-catching-drift)，社区，2026，原文为示意场景）✅。该文还称「60-70% 的破坏性改动能通过 code review 而不被发现」，但只笼统归因于「对 API 事故的研究」，无具体出处，仅作方向性参考 ⚠️。

还要防一个更隐蔽的自我欺骗：「后端能启动、返回 200、测试全绿」不等于契约严谨。AI 会精确地做你要求的事，而且只做这么多——你说「make it work」，它就让它能跑，不会主动补 schema 校验和契约纪律。原文写得很直白：「一个能启动、能返回 200 的后端，感觉像做完了。它没做完，它只是暂时还没报错而已」（[Stack Overflow Blog](https://stackoverflow.blog/2026/06/23/your-ai-shipped-a-backend-that-boots-that-is-the-whole-problem/)，社区，2026-06）✅。

所以解法是把「对齐」从记忆里拿出来，交给一个独立于两个实现之外的第三方真值源。契约还能反过来帮 AI：没有 spec 时它只能从代码或文档里推断 API 行为，容易出错和幻觉；有结构化契约就替人和 AI 都消除了猜测（[Kinde](https://kinde.com/learn/ai-for-software-engineering/using-ai-for-apis/spec-driven-apis-designing-and-building-services-the-ai-friendly-way/)，社区，2026）✅。学术侧也有量化，有 spec 能让 LLM 生成代码的错误率最高降 50%（[arXiv:2602.00180](https://arxiv.org/html/2602.00180v1)，学术，2026）✅，这个数字是论文对 controlled studies 的转述，看方向就行。

这和 [#042](../05-质量保证/042-幻觉API与幻觉依赖.md)（幻觉 API）是同源问题：契约就是当场戳穿 AI 编造字段和端点的那把尺子。

## 怎么做

按「先决策、再搭工作区、再管契约、最后走流程」的顺序做。

**第一步，决策：能合就合。** 强耦合的前后端优先考虑 monorepo（[#050](./050-大仓库monorepo里不迷路.md)），不能合再往下走。

**第二步，搭工作区：把要协同的仓变成并列的子目录。** 三种方式，从轻到重：

- 临时协作：`claude --add-dir ../backend`，当次会话把后端拉进来。
- 固定协作：把相邻路径写进 `.claude/settings.json` 的 `additionalDirectories`（团队共享），或写进 `.claude/settings.local.json`（个人）。
- 长期多仓：建一个元仓库当父工作区，用清单文件管住一组仓，作为「有全景的起点」。

**第三步，补上被丢掉的说明书。** 用 `--add-dir` 加上 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`，让相邻仓的 CLAUDE.md 也进上下文；或者在元仓库顶层写一份跨仓 CLAUDE.md，指明每个仓是什么、约定在哪。

**第四步，立契约当唯一真值源，让两边实现从它派生。** 分三小步：

1. 选载体。REST 接口用 OpenAPI（server stub、client SDK、文档都能从它生成）；前后端同语言（比如都是 TS）用共享类型包或 tRPC，编译器直接当裁判，最省事；强类型跨服务用 GraphQL schema 或 Protobuf。原则一致：先于任何代码写出一份正式规格，让它充当唯一真值源（来源：Kinde ✅）。
2. 立规矩：改接口先改契约。所有对 API 的改动，无论多小，都必须从更新规格开始（原文「no matter how small, must start with an update to the specification」，来源：Kinde ✅）。把这条写进工作区顶层 CLAUDE.md。
3. 让代码从契约生成，别手抄。改完 schema 就跑 codegen 产出类型和 client。代码是重新生成而不是手工编辑的，spec 和代码天生就对齐（来源：arXiv:2602.00180 ✅）。

**第五步，CI 当硬闸门，把纪律变成机器强制。** 三道闸，按需上：

- spec-diff：每个 PR 跑 `oasdiff` 检测破坏性改动（改名字段、删端点、改类型），一旦 breaking 就挡下。
- 契约测试：`Schemathesis` 从 spec 生成基于属性的测试用例（property-based，指按 spec 里的类型约束自动造大量输入），打真实运行的 API，验证响应是否真的符合 spec；`Specmatic` 在 CI 里校验实现是否匹配 spec，不匹配就让构建失败。
- spec lint：`Spectral` 检查契约本身的质量，比如字段命名是否一致、参数是否都有描述。

只当参考文档、不进 CI 的契约没有约束力——没被强制执行的 spec 只是一份愿望文档，而不是对 API 行为的可靠描述。

**第六步，流程纪律：一次会话改完两边，并把计划写进文件。** 官方对「跨边界一次改动」的两条法则同样适用于多仓：

- 「Give Claude the whole change in one session」，把「改接口」加「改所有调用点」放进同一会话，决策才一致。别拆成「先开个会话改后端，再开个会话改前端」。
- 「Save the plan to a file before editing」。长会话会自动压缩历史，把跨仓改动清单写进 markdown 文件，计划就能活得比对话历史久（[Claude Code 文档：large-codebases](https://code.claude.com/docs/en/large-codebases)，官方）✅。

**第七步，两边都验证，而且用一条命令跑完。** 手动切目录跑两遍，实际操作里很容易只跑一边。在工作区根放一个 `verify.sh`，让 AI 改完直接跑它（可复制件见下面「手段 C」，验证体系见 [#040](../05-质量保证/040-怎么验证AI代码是真的对.md)）。

## Claude Code 实战

### 手段 A：`--add-dir`，当次会话拉进另一个仓

目录结构如下，前后端各自独立克隆，互为并列的子目录：

```text
workspace/
  backend/     # 后端仓，含自己的 CLAUDE.md
  frontend/    # 前端仓，从这里启动 claude
```

```bash
cd frontend
# 只给文件访问，后端 CLAUDE.md 不加载：
claude --add-dir ../backend

# 让后端的 CLAUDE.md / rules 也进上下文（守后端规范的关键）：
CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 claude --add-dir ../backend
```

会话里就能这样让它干活：「给用户加 `phone` 字段。后端 `../backend/src/routes/users.ts` 加校验和落库，前端这边同步表单和类型，两边都改。」

**怎么判断做对了：** 在会话里运行 `/context`，看 **Memory files** 那一栏。官方文档明说这一栏列出当前加载了哪些 CLAUDE.md（官方，2026-08 核实）✅。

- 只跑 `claude --add-dir ../backend`：这一栏里**不该**出现 `../backend/CLAUDE.md`。
- 带上 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`：这一栏里**应该**多出 `../backend/CLAUDE.md`。

如果带了环境变量也没出现，先确认后端目录是用 `--add-dir` 加的，而不是写在 `additionalDirectories` 里——官方明确说该环境变量对 `additionalDirectories` 无效。

### 手段 B：`additionalDirectories`，固定协作写进 settings

在前端仓的 `.claude/settings.json` 里配（团队共享，提交进 git）：

```json
{
  "permissions": {
    "additionalDirectories": ["../backend"]
  }
}
```

记住官方那张表：这种写法永远不加载后端的 CLAUDE.md 和 skills，只给文件权限。

要说明书，就走手段 A 的环境变量，或者把后端约定的关键条目提炼进前端 CLAUDE.md 或元仓库顶层文件。个人临时用则放 `.claude/settings.local.json`。

### 手段 C：元仓库（虚拟 monorepo），长期多仓的「全景起点」

这是社区里两篇实践文章都收敛到的同一个模式：建一个不含业务代码的父仓当工作区根，里面只放组织性的脚手架，也就是仓清单、跨仓 CLAUDE.md、跨仓脚本。各业务仓作为子目录克隆进来，并用 gitignore 忽略掉，各自保留自己的 git origin，push 照旧回各自的远端。

两个来源：[Karun Japhet: Structuring Claude Code for Multi-Repo Workspaces](https://karun.me/blog/2026/03/26/structuring-claude-code-for-multi-repo-workspaces/)（社区，2026-03）✅，和 [Rafferty Uy: Repo-of-Repos Pattern](https://raffertyuy.com/raztype/repo-of-repos-pattern/)（社区，2026-05）✅。前者用 `mani.yaml` 分文件管清单，后者用 `repos/repos.yaml` 加自动生成的 `repos.md`。骨架是一样的。

#### 可复制骨架

下面这份最小骨架合并了两篇的做法，四个文件就能跑起来。

目录结构：

```text
workspace/                      # 元仓库，自己是一个 git 仓
  CLAUDE.md                     # 跨仓说明书（提交）
  repos.yaml                    # 仓清单，唯一真值源（提交）
  verify.sh                     # 一条命令验两边（提交）
  .gitignore
  backend/                      # 独立 git 仓，被 gitignore
  frontend/                     # 独立 git 仓，被 gitignore
```

`repos.yaml`——每个仓一行描述，这行描述决定 AI 能不能找对地方：

```yaml
projects:
  backend:
    desc: 用户与订单 REST API，Node.js + Express + TypeScript + PostgreSQL
    url: git@github.com:acme/backend.git
    path: backend
    tags: [api, node]

  frontend:
    desc: 后台管理界面，React + Vite + TypeScript，调用 backend 的 REST API
    url: git@github.com:acme/frontend.git
    path: frontend
    tags: [ui, react]
```

字段名 `desc` / `url` / `path` / `tags` 取自 mani 这个多仓管理 CLI 的配置格式（[alajmo/mani](https://github.com/alajmo/mani)，开源工具，2026-08 核实）✅。装了 mani 就能 `mani sync` 一次性克隆全部；不想引入工具，这份 yaml 当纯清单给 AI 读也完全够用。

`.gitignore`——子仓目录写成 `backend/`，末尾带斜杠，别写 `backend/*`：

```gitignore
backend/
frontend/
```

这里有个反直觉的点，值得单独说清楚。网上不少元仓库示例写的是 `orders/*` 这种带 `/*` 的形式，那是因为在原文里 `orders/` 只是一个业务分组目录、它本身不是 git 仓，`/*` 才能匹配到里面的条目并允许后面写 `!` 例外。但子仓目录本身是一个独立 git 仓，git 把嵌入仓当作**单一路径** `backend` 处理，不会去遍历它内部的条目，所以 `backend/*` 匹配不上，等于没写。

实测（本地真实建仓验证，2026-08）：

```bash
# 用 backend/* 时，忽略不生效
$ git status --short
?? .gitignore
?? backend/
?? frontend/

# 而且此时 git add . 会把子仓当 gitlink 塞进索引
$ git add .
warning: adding embedded git repository: backend

# 换成 backend/ 后才真正干净
$ git status --short
?? .gitignore
```

顺带说明为什么不能写 `!backend/CLAUDE.md` 这类例外：父仓无法单独追踪嵌入仓内部的文件，这条例外在这个骨架里永远不会生效。跨仓说明书写在元仓库顶层的 `CLAUDE.md` 里，不要试图从父仓追踪子仓里的文件。

用 `backend/*` 的直接后果，就是本篇反模式里那条「在元仓库根 `git add .` 提交子仓改动」——顶层 CLAUDE.md 明令禁止的事，会因为忽略没生效而被 AI 一把做掉。

顶层 `CLAUDE.md`——只写工作区规则和「去哪里查」，不硬抄仓列表：

```markdown
# 多仓工作区

这个目录不是一个普通项目，它是多个独立 git 仓的父工作区。
每个子目录（backend/、frontend/）是**独立的 git 仓**，有自己的 origin。

## 有哪些仓、分别是什么

看 `repos.yaml`，每个 project 的 `desc` 字段说明了它是什么。
不要凭记忆假设某个仓存在或不存在，先读 repos.yaml。

## 跨仓改动规则

1. 动手前先把改动清单写进 `_plans/<日期>-<改动名>.md`，包含：要改哪几个仓、每个仓改哪些文件、接口字段的最终名字。
2. 一次会话内改完所有涉及的仓，不要分多次会话。
3. 接口字段名以契约文件为准（见各仓 README 指向的 schema），不要在两边分别起名。
4. 改完必须在工作区根运行 `./verify.sh`，两个仓都过了才算完成。

## git 规则

- 不要在 workspace 根 commit 子仓里的改动，子仓改动在子仓目录内 commit。
- 每个仓单独开分支、单独提 PR。
```

`verify.sh`——一条命令验两边，这是防「只跑一边」的关键件：

```bash
#!/usr/bin/env bash
# 跨仓验证：任一仓失败即整体失败
set -uo pipefail

# 锚定到脚本所在目录，这样在任何 cwd 下调用都能跑对
cd "$(dirname "${BASH_SOURCE[0]}")"

fail=0

run() {
  local dir="$1"; shift
  echo "=== $dir: $* ==="
  if (cd "$dir" && "$@"); then
    echo "--- $dir OK"
  else
    echo "--- $dir FAILED"
    fail=1
  fi
}

run backend  npm run typecheck
run backend  npm test
run frontend npm run typecheck
run frontend npm test

if [ "$fail" -ne 0 ]; then
  echo "VERIFY FAILED"
  exit 1
fi
echo "VERIFY OK (backend + frontend)"
```

**怎么判断做对了：**

```bash
chmod +x verify.sh
./verify.sh; echo "exit=$?"
```

两边都通过时，最后两行是：

```text
VERIFY OK (backend + frontend)
exit=0
```

任一仓的 typecheck 或测试挂掉时，会看到对应的 `--- frontend FAILED`，末尾是 `VERIFY FAILED` 和 `exit=1`。注意脚本用的是 `set -uo pipefail` 而不是 `set -e`——故意的，要让两个仓都跑完再汇总，否则后端一挂你就看不到前端的情况了。

把 `npm run typecheck` / `npm test` 换成你项目真实的命令即可（Java 换 `./gradlew check`，Python 换 `mypy .` 和 `pytest`）。

#### 三层 CLAUDE.md

Claude Code 加载 CLAUDE.md 时会从当前目录往上逐级读父目录（官方，2026-08 核实）✅，所以从 `workspace/backend/` 启动时，`workspace/CLAUDE.md` 和 `workspace/backend/CLAUDE.md` 都会进上下文。这就是三层分工的基础：

| 层 | 位置 | 写什么 |
|----|------|--------|
| 工作区级 | `workspace/CLAUDE.md` | 多仓警告、去 repos.yaml 查仓、跨仓操作规则。刻意写短 |
| 团队级（可选） | `workspace/orders/CLAUDE.md` | 一组仓共用的技术栈约定和例外 |
| 仓级 | `workspace/backend/CLAUDE.md` | 该仓的构建命令、架构、工具链，跟平时一样，由仓的 owner 维护 |

团队级这层只有当仓多到需要按业务域分组时才需要（Karun 原文的例子是 `orders/`、`shipping/`、`infra/` 各一层）。两三个仓就别加，直接工作区级加仓级两层。

从元仓库根启动 `claude`，AI 一开始就有跨仓全景，再顺着 `repos.yaml` 进具体的仓干活。

### 手段 D：把契约纪律写进 CLAUDE.md，让改动 contract-first 走

在工作区顶层（或后端仓）的 CLAUDE.md 里把规矩定死，让 AI 每次动接口都从契约起步：

```markdown
## API 契约纪律
- 本项目接口契约在 `api/openapi.yaml`，它是唯一真值源。
- 改任何接口（字段/端点/类型）必须先改 openapi.yaml，再改实现。
- 前端类型不许手写，一律 `pnpm gen:api` 从 openapi.yaml 生成。
- 改完接口必须在前后端各自跑 typecheck + 契约测试。
```

然后在同一个会话里让它走完「改契约 → 生成 → 改两边 → 双边验证」：

```text
给 User 加 phone 字段，contract-first 走：
1. 先改 api/openapi.yaml：User schema 加 phone: string，标注是否必填
2. 跑 `pnpm gen:api` 重新生成前端 client 类型
3. 后端 handler 加校验和落库，字段名严格对齐 openapi.yaml
4. 前端表单/调用点用生成出来的类型，编译器保证字段名一致
5. 后端跑契约测试(schemathesis)，前端跑 typecheck，两边都过再报完成
```

**怎么判断做对了：** 故意在后端把 `phone` 改成 `phoneNumber` 而不动 openapi.yaml，然后跑 `oasdiff` 或契约测试。做对的话 CI 当场失败并指出这是一处破坏性改动（oasdiff 会给出严重级别和文件行号）；如果两边都绿，说明闸门没接上，你的契约还只是文档。

> 提示：`oasdiff` 官方提供 MCP server，可以让 Claude Code 直接调用它对比两版 spec，动手前就知道这次改动会不会破坏消费方（工具官网，2026-07 核实）✅。

这跟 [#040](../05-质量保证/040-怎么验证AI代码是真的对.md) 讲的「约束层（类型 / schema）当独立真值源」是同一条原则，只是落到了接口场景。

## 横向对比

| 工具 | 多仓解法 | 契约治理解法 | 差异 |
|------|---------|------------|------|
| **Claude Code** | 用 `--add-dir` / `additionalDirectories` 拉相邻仓；元仓库工作区；跨仓 CLAUDE.md 分层 | 在 CLAUDE.md 里定 contract-first 纪律，让 AI 跑 codegen 和契约测试；可挂 `oasdiff` MCP 在改前查破坏性改动 | 官方原生支持多目录访问；但 `additionalDirectories` 不加载对方 CLAUDE.md 和 skills，需环境变量补 |
| **Cursor** | 多根工作区；社区长期在请求「跨窗口、跨仓的 agent 通信」，让前端 agent 和后端 agent 能互相请求 | 在 rules 文件里写契约约定，同样接 OpenAPI codegen 和契约测试 | 跨窗口协同仍停在功能请求阶段（社区论坛）⚠️ |
| **GitHub Copilot** | background agent 默认在单个仓的上下文里表现最好，官方建议拆成针对单个仓的子任务逐个做，最后测集成点 | 同样靠 OpenAPI 或共享类型当真值源，加 CI 契约门；没有契约专属特性 | 多仓需手动拆解协调（[GitHub 社区讨论](https://github.com/orgs/community/discussions/186469)，官方论坛）✅ |

共性趋势是：三家都在补「跨仓依赖」这块短板。社区普遍收敛到两类解法。一类是工作区打包，把依赖的仓拉进一个工作区，仓数量不超过 3 个时最省事。另一类是元仓库或显式依赖图，规模大或跨语言时才值得。选哪种看仓的数量和团队规模，别一上来就上重方案。

契约这一侧则三家没差别：工具本身都不「管」契约漂移，真正兜底的是 CI 里那道机器闸门（spec-diff 加契约测试加 codegen）。工具的差异只在「多方便把契约纪律喂给 AI」。

## 反模式

- ❌ **明明能合 monorepo 却硬维护多仓给 AI 添堵。** 分仓要有真实理由（团队、权限、发布），否则先合仓（[#050](./050-大仓库monorepo里不迷路.md)），比任何跨仓配置都省心。
- ❌ **以为 `additionalDirectories` 拉进后端就万事大吉。** 它只给文件权限，不加载后端的 CLAUDE.md 和 skills（官方明确），AI 会不守后端规范。要说明书得用 `--add-dir` 加 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`。
- ❌ **开两个会话分别改前后端。** 这是决策不一致、字段对不上的高发姿势。官方法则是「一次会话改完整改动」，跨仓改动放同一会话。
- ❌ **让 AI 手抄类型到另一个仓来保持一致。** 手抄就是漂移之源。有契约就跑代码生成，让类型系统当裁判（做法见「怎么做」第四步和「手段 D」）。
- ❌ **「后端能启动、测试全绿」就当接口做完了。** 它只是暂时还没报错而已（来源：Stack Overflow Blog ✅）。绿测试常常只覆盖顺利路径（happy path），验不到 schema 严谨性和契约一致性。
- ❌ **先写代码、事后补 spec。** spec 会立刻烂掉，沦为没人对齐的愿望文档。改动必须从更新规格开始（来源：Kinde ✅）。
- ❌ **指望 code review 挡住 schema 漂移。** 评审者盯业务逻辑、不盯 spec 一致性，这是结构性盲区（来源：TotalShiftLeft ✅）。要靠 CI 里的 spec-diff 和契约测试自动拦。
- ❌ **契约只当参考文档、不进 CI。** 没有强制执行的 spec 只是一份愿望文档，而不是对 API 行为的可靠描述。
- ❌ **只在一边验证就宣告完成。** 改了后端只跑后端测试，前端调用点是否对上没验。把两边的检查收进工作区根的 `verify.sh`，别指望自己每次都记得切目录跑两遍。
- ❌ **在元仓库根 `git add .` 提交子仓改动。** 子仓有自己的 origin，改动要在子仓目录内 commit。这条必须写进工作区级 CLAUDE.md，否则 AI 很容易在父仓里一把 add 掉。
- ❌ **在 CLAUDE.md 里硬抄各仓清单或接口列表。** 清单会过期变成化石（同 [#010](../02-上下文工程/010-CLAUDE-md怎么写才生效.md) 的反模式），应改成指向权威来源的指针（清单文件、schema 文件）。
