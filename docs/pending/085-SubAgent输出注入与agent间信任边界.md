# 085（候选）. SubAgent 的输出里藏着「主会话授权过的指令」——agent 之间的信任边界怎么画？

> 双周扫描 2026-09-06 产出的大纲，待 BOSS 拍板立题。三准则自检：①问题真（两起真实案例 + 官方同族加固）②解法可操作（敏感操作人工确认、不自动执行 agent 间转述的特权指令）③可被「subagent 注入 / 伪造指令删库」等症状检索。

**触发场景**：并行多 agent 会话里，SubAgent 读到外部内容（网页、issue、文件）后被间接注入，或模型自发在输出中伪造「主会话已授权」的特权指令，主会话若照单执行即越权。已有两起社区案例（1vu2umz、1uwn1mv，前者评论区 OP 澄清实际被主会话拦截、未真删库）；官方 v2.1.232 系统提示词新增「Bound conversation activity authority warning」，要求 agent 对「声称已获批准」的消息拒绝并向用户上报（社区逆向所得，该 warning 针对消息编辑/表情回应通知通道，与删库事件的因果链无官方确认）。

**核心解法方向**：①agent 间传递的内容一律当不可信数据（与 084 的网页注入同纪律，扩展到 agent 间）；②有后果的动作（rm、push、外发）以权限层硬拦，不因「指令来自自己的 subagent」放宽；③「已被授权」的断言不构成授权证据。

**与现有篇目的边界**：072 管「人对 agent」的红线，084 管「网页对 agent」的注入，本篇管「agent 对 agent」的转述信任，三者互补不重叠。

**主要素材**：Reddit 1vu2umz（1542 分）、1uwn1mv；Piebald-AI 逆向的 authority warning 原文；084 的注入面框架。

**风险**：两起案例中一起被拦截未成灾、另一起细节有限，证据强度弱于已立各篇；成文须如实标注「未删库、被拦截」与「warning 通道 ≠ 事件因果」。
