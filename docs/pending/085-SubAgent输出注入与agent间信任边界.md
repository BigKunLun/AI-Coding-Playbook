# 085（候选）. SubAgent 的输出里藏着「主会话授权过的指令」——agent 之间的信任边界怎么画？

> 双周扫描 2026-09-06 产出的大纲，09-20 与 10-04 两度增补证据。待 BOSS 拍板立题。三准则自检：①问题真（两起真实案例 + 官方同族加固 + 官方落地防护 + 攻击侧研究）②解法可操作（敏感操作人工确认、不自动执行 agent 间转述的特权指令、共享缓存隔离）③可被「subagent 注入 / 伪造指令删库 / agent 蠕虫」等症状检索。

**触发场景**：并行多 agent 会话里，SubAgent 读到外部内容（网页、issue、文件）后被间接注入，或模型自发在输出中伪造「主会话已授权」的特权指令，主会话若照单执行即越权。已有两起社区案例（1vu2umz、1uwn1mv，前者评论区 OP 澄清实际被主会话拦截、未真删库）。

**2026-09 的两条一手证据（立题理由升级）**：
- **平台已响应**：CHANGELOG v2.1.271（09-14）subagent 改经专用 hand-back 调用回报、由安全分类器审查；v2.1.277（09-18）subagent 结果带 header 标记与缩进送达主 agent，官方原文「text in a subagent's result cannot pass as the session's own instructions」，同版把 workflow 脚本计算的 agent() 提示标注为脚本文本——官方承认为真实威胁面并做了输出信道加固。
- **攻击侧官方确认**：Anthropic 09-10 威胁情报报告（154 页）记载攻击者对 LiteLLM / OpenClaw 部署做 prompt injection 窃取生产 API key——agent 链路上的注入窃钥已是被观测到的野外行为，不只是理论。

**2026-10 增补（第三期证据）**：
- 攻击面研究侧：Matthew Green「agent 蠕虫的两半」——「一个劫持 agent 的载荷，和一个把载荷带给下一个 agent 的载体」，沙箱内 agent 可通过**共享包缓存**互相留指令、改变彼此行为（沙箱不隔离共享缓存即不隔离传播）——agent 间信任边界从「输出信道」扩展到「共享资源信道」。
- 官方持续演进：v2.1.284 对 MEMORY.md 与召回记忆中和仿冒 Claude Code 标记的不可见字符（记忆通道注入防御）；v2.1.287 上线内置 mod「You should know」（侧翼监督 agent 标记主副 agent 可能遗漏的事，288 进一步按责任方区分措辞）——官方在把「跨 agent 监督」产品化。
- 社区信号：10-03 有帖报告「已批准的 MCP server 事后可静默改写自己的指令」（1wwr4vy，标题级，待下期正文确认）——被批准 ≠ 保持可信，与 Notion 广告注入同族。

**核心解法方向**：①agent 间传递的内容一律当不可信数据（与 084 的网页注入同纪律，扩展到 agent 间）；②有后果的动作（rm、push、外发）以权限层硬拦，不因「指令来自自己的 subagent」放宽；③「已被授权」的断言不构成授权证据。官方 277 的 header 加固是同方向的平台侧实现，成文时作为「平台做了什么/你还需做什么」对照。

**与现有篇目的边界**：072 管「人对 agent」的红线，084 管「网页对 agent」的注入，本篇管「agent 对 agent」的转述信任，三者互补不重叠。

**主要素材**：Reddit 1vu2umz（1542 分）、1uwn1mv；官方 CHANGELOG v2.1.271/277 条目原文；Anthropic 威胁情报报告 September 2026（LiteLLM/OpenClaw 注入窃钥）；084 的注入面框架。

**风险**：两起案例中一起被拦截未成灾、另一起细节有限；官方 header 加固针对的是「冒充主会话指令」，不等于覆盖全部 agent 间注入路径。成文须如实标注「未删库、被拦截」与防护的边界。
