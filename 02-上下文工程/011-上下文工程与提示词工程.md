# 011. 为什么 prompt 写得很细，Claude 还是越跑越偏？

> 难度：中级
> 主题：上下文工程
> 工具：Claude Code · 横向(Cursor / Copilot)
> 题型：决策题

> ⏰ 时效声明：**2026-08-03** 复核。文中 `/compact`、`/clear`、`/context`、subagent 文件格式、MCP tool search 的 `ENABLE_TOOL_SEARCH` 写法，均对照 Claude Code 官方文档（code.claude.com/docs）确认。第三方工具（Cursor / Copilot）的具体参数易变，只写机制不写数字，以各家官方文档为准。

## TL;DR

你写了一份很细的 prompt 或 CLAUDE.md，前十轮 Claude 很听话，跑到几十轮之后开始违反你开头定下的规矩。这不是 prompt 写得不够好，是**上下文（context）被工具输出撑满了，你的指令被稀释了**。

术语一句话：prompt 是你写的那段字符串；context 是每次调模型时真正送进去的全部 token——system prompt、CLAUDE.md、对话历史、工具返回结果、检索片段全算在内。你只控制了第一项。

对号入座：

| 症状 | 大概率原因 | 直接动作 |
|---|---|---|
| 跑几十轮后忘了开头的约束（"不许改测试"之类） | 指令被后续工具输出淹没 | `/context` 看占比 → `/compact` 带上约束再说一遍 |
| 换了个任务，Claude 还在提上一个任务的文件 | 陈旧上下文没清 | `/clear` 后重开 |
| 一次让它读全仓库，之后回答开始胡说 | context rot：越长越记不住 | 改成按需读文件，不预塞 |
| 接了几个 MCP server 后，可用上下文肉眼变少 | 工具定义占了窗口 | 确认 `ENABLE_TOOL_SEARCH` 没被关掉（默认开） |
| 子任务（查资料、跑日志）把主对话搞脏 | 没做隔离 | 丢给 subagent，只回传结论 |

结论一句话：长任务里，**写指令的杠杆在下降，管上下文的杠杆在上升**。prompt engineering 没死，它是上下文工程里的一个环节。

---

## 为什么

### 1. 一个真实现场

你在 CLAUDE.md 里写清楚了："改动前先跑 `pytest`，不许修改 `tests/` 下的文件。"

前几轮完全正常。然后你让它修一个跨 8 个文件的 bug。它开始 Grep、Read、跑测试、看报错、再 Read……三十几轮工具调用之后，你发现它删掉了一个断言，理由是"这个测试和新实现不符"。

你的指令一个字都没变，还在上下文里躺着。变的是它周围多了大量文件内容和报错日志。模型每一轮都在重新读整个上下文，你那两行约束占的比重被这些新增内容不断稀释——具体掉到多少没法给一个通用数字，但可以自己量：跑 `/context`，对比任务刚开始和三十轮之后 CLAUDE.md 与 Messages 两行的 token 数，比值一目了然。

这就是 prompt engineering 和 context engineering 的分界线：**前者管你写了什么，后者管模型实际看到的那一整包东西长什么样。**

Anthropic 官方把上下文工程定义为提示工程的「自然演进」（natural progression），不是替代：提示工程是"写好并组织给模型的指令"，上下文工程是"在推理时管理好要喂进去的整套 token，包括所有 prompt 之外的信息"，而且它是**迭代**的——每次决定传什么给模型都要重做一遍（[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)，官方，2025-09）。

| 维度 | Prompt Engineering | Context Engineering |
|------|-------------------|---------------------|
| 工作单元 | 一段文本 | 推理时刻的整个上下文窗口 |
| 包含内容 | 指令 + few-shot 示例 | 指令 + 历史 + 工具结果 + 检索 + 记忆 + 输出格式 |
| 静态/动态 | 一次写定 | 运行时按任务组装 |
| 发生时机 | 离线、一次性 | 每一轮都发生 |

### 2. 根因 A：上下文越长，模型越记不住

Anthropic 引用大海捞针类研究，把这个现象叫 **context rot（上下文腐烂）**：上下文窗口里的 token 越多，模型准确回忆其中信息的能力越差；所以上下文要当成"边际收益递减的有限资源"（官方，2025-09）。

学界更早就有实证：模型对长上下文中**位于中间**的信息回忆显著变差，即使是专为长上下文设计的模型也一样，这个现象叫 "lost in the middle"（[arXiv:2307.03172](https://arxiv.org/abs/2307.03172)，学术，2023-07，2023-11 修订）。

对你的直接含义：**"全塞进去更保险"是错的。** 你的约束越靠前、周围垃圾越多，被忽略的概率越高。

### 3. 根因 B：agent 的上下文是"活的"，只会涨不会降

LangChain 的说法是：长程任务加上不断累积的工具调用反馈，会让 agent 用掉大量 token，后果是超窗口、成本延迟暴涨、表现下降（[Context Engineering for Agents](https://www.langchain.com/blog/context-engineering-for-agents)，社区权威，LangChain，2025-07）。

数量级上，一个典型 agent 任务需要几十次工具调用（Manus 团队披露约 50 次，见 [Latent Space 访谈 Lance Martin](https://www.latent.space/p/context-engineering-for-agents-lance)，社区，2025-09）。每次调用的返回值都进上下文，而且不会自己出去。

你在第 0 轮写的 prompt，无法预判第 30 轮需要什么、又该扔掉什么。这是 prompt 单独解决不了的问题。

### 4. 根因 C：可调的旋钮变多了

单轮聊天里，system prompt 几乎是唯一杠杆，所以叫「prompt engineering」名副其实。多轮 agent 里，可调维度一下子多出来：什么时候检索什么、工具结果留不留、历史压不压、要不要拆 subagent 隔离。写指令仍然重要，但它只是其中一项。

Anthropic 给的原则是：模型的注意力预算有限，好的上下文工程就是找到**能达成目标的最小一组高信号 token**（官方，2025-09）。

Philipp Schmid 的总结被引用最多："如今大多数 agent 失败已经不是模型失败，而是上下文失败"（[The New Skill in AI is Not Prompting, It's Context Engineering](https://www.philschmid.de/context-engineering)，社区权威，2025-06）。

### 5. "prompt engineering 已死"这话别信

有一派喊 prompt engineering 已死（比如 MarTech 的 ["Prompt engineering is dead. Long live context engineering"](https://martech.org/prompt-engineering-is-dead-long-live-context-engineering/)，社区，2025-07）。但官方用的词是「自然演进」，Simon Willison 的解释更准：换名字赢，是因为旧名字被大众理解成"往聊天框里打字的一个自命不凡的说法"，而不是技能本身作废（[Context engineering](https://simonwillison.net/2025/jun/27/context-engineering/)，社区权威，2025-06）。

实用的分法来自 Drew Breunig：**prompt 是写给聊天机器人的一次性请求，context 是为应用维护、不断演化的指令；两者没有高下，只是用途不同**（[Prompts vs. Context](https://www.dbreunig.com/2025/06/25/prompts-vs-context.html)，社区，2025-06-25）。

> 小C 的判断：你在聊天框里问一句就走，写好 prompt 够了。你在 Claude Code 里跑一个要几十轮工具调用的任务，那就是上下文工程问题，改 prompt 的措辞收益很小。

## 怎么做

下面六步都对应一条能敲的命令或能抄的配置。

### 第一步：先量，别猜

跑 `/context`。它把当前上下文占用画成彩色网格，按项目分行（System prompt / CLAUDE.md / Skills / MCP tools / Messages 等），并给优化建议。想看逐项明细就跑 `/context all`（官方，[commands 参考](https://code.claude.com/docs/en/commands)，2026-08 核对）。

判据（以下阈值是经验参考，官方没有给出推荐值，按自己的任务调）：

- Messages（对话与工具结果）占比超过一半 → 该压缩或清空了。
- MCP tools 一行占了上万 token → 见第五步。
- CLAUDE.md 一行明显超过常驻内容里的其他项 → 太长了，拆成按需加载的 skill 或 rules。

### 第二步：任务边界到了就 `/clear`，别硬撑

```
/clear
```

`/clear` 开一个空上下文的新会话；可以带一个名字（`/clear 支付重构`）给旧会话打标签，之后用 `/resume` 找回（官方 commands 文档）。

判据：换了一个不共享文件的新任务 → 一律先 `/clear`。留着旧上下文既烧钱又制造干扰。

### 第三步：必须接着干的长任务，用带指令的 `/compact`

```
/compact 保留：不许修改 tests/ 目录、改动前必须跑 pytest、当前正在改 payments/refund.py
```

`/compact [instructions]` 会把对话摘要成一段，释放空间，而你传的 instructions 决定摘要保留什么（官方 commands 文档）。**这是让你的核心约束"活过压缩"的唯一手段**——不写 instructions，约束大概率被摘掉。

验证：`/compact` 结束后立刻跑 `/context`，Messages 一行的 token 应显著下降；再问一句"复述一下当前的硬约束"，答案里必须包含你写进 instructions 的那几条。答不出来说明约束丢了，重新说一遍。

### 第四步：脏活丢给 subagent，只让结论回主上下文

subagent 有自己独立的上下文窗口、系统提示和权限，工作完只把摘要回传主会话（官方，[Subagents](https://code.claude.com/docs/en/sub-agents)）。查资料、翻日志、遍历大目录这类会产出大量一次性文本的活，全该走这条路。

可复制：新建 `.claude/agents/log-digger.md`（项目级）或 `~/.claude/agents/log-digger.md`（个人全局）：

```markdown
---
name: log-digger
description: 翻查测试报错与运行日志，只回传结论与关键行号，不回传原始日志
tools: Read, Glob, Grep, Bash
model: sonnet
---

你负责在日志与测试输出里定位问题。

规则：
1. 只回传结论、涉及的文件与行号、最多 10 行关键原文。
2. 绝不把整份日志或整个文件内容回传给主会话。
3. 找不到就直接说找不到，不要猜。
```

注意 `tools` 里带了 `Bash` 就意味着这个 subagent 能写文件、能执行命令——想要真只读，就删掉 `Bash`，只留 `Read, Glob, Grep`。

验证：文件存下后几秒内生效，不必重启（官方文档：Claude Code 监听这两个目录）。官方列了两种仍需重启的情况：一是这个 `agents/` 目录在会话启动之后才新建（监听只覆盖会话启动时已存在的目录）；二是会话用 `--disable-slash-commands` 启动，这种会话根本不监听这两个目录（官方 Subagents 文档，2026-08 核对）。生效判据：让 Claude 干一件该委派的活，主会话里应只出现摘要，跑 `/context` 时 Messages 增量远小于你手动读日志。

### 第五步：MCP 接多了，确认 tool search 是开的

Claude Code 默认开启 MCP tool search：会话启动时只加载工具名和 server 说明，工具的完整定义等用到时才拉进来，所以多接几个 server 对上下文影响很小（官方 [MCP 文档](https://code.claude.com/docs/en/mcp)，2026-08 核对）。

它会在这几种情况下被关掉：设了 `ENABLE_TOOL_SEARCH=false`；设了 `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`；`ANTHROPIC_BASE_URL` 指向非官方主机（多数代理不转发所需的 `tool_reference` 块）；或模型不支持 `tool_reference`（需要 Sonnet 4.5 / Haiku 4.5 / Opus 4.5 及之后的模型）。

想显式打开、或改成"能装下就先装、装不下才延迟"：

```json
{
  "env": {
    "ENABLE_TOOL_SEARCH": "true"
  }
}
```

写进 `.claude/settings.json`（项目）或 `~/.claude/settings.json`（个人）。`ENABLE_TOOL_SEARCH=auto` 是阈值模式：工具定义能塞进上下文窗口 10% 以内就一次性加载，超出的部分才延迟（官方 MCP 文档）。

例外：某个 server 的工具每轮都要用，可以在该 server 配置里设 `"alwaysLoad": true`，它的全部工具就在启动时进上下文。代价是这些 token 一直占着，只对少量工具这么干。

验证：跑 `/context`，看 MCP tools 那一行。tool search 生效时它应该只是工具名的量级；关掉后同样的 server 会明显更大。

### 第六步：默认按需加载，不预塞

Anthropic 推荐的做法是在上下文里只保留轻量引用（文件路径、查询语句、链接），运行时用工具按需加载，而不是提前把所有数据塞进去（官方，2025-09）。Claude Code 处理大仓库就是这个套路。

落到手上的两条：

- 不要一上来"把整个 `src/` 读一遍"。给它入口文件和目标，让它自己 Grep。
- CLAUDE.md 只写"每次都要遵守的事实和约束"，长流程写成 skill——skill 的正文只在被用到时才加载，放着基本不花 token（官方 [skills 文档](https://code.claude.com/docs/en/skills)）。

另外，别往 prompt 里堆边缘情况清单（官方原话反对 "stuff a laundry list of edge cases into a prompt"），也别把工具集堆臃肿——官方把"覆盖过多功能的臃肿工具集"列为最常见的工具失效模式（官方，2025-09）。

## 横向对比

三家 AI 编码工具在"上下文"上的机制差异（只列机制，具体数值参数变化快，以各家官方文档为准）。

| 维度 | Claude Code | Cursor | GitHub Copilot |
|------|------------|--------|----------------|
| 持久项目上下文 | `CLAUDE.md`（多层级）+ `.claude/rules/*.md`（可按 glob 条件加载） | `.cursor/rules/*.mdc`（Always / Auto / Glob / Manual 四种激活） | `.github/copilot-instructions.md`（仓库根单文件） |
| 上下文压缩 | `/compact [instructions]` + 接近上限时自动压缩 + `/clear` | Max Mode——偏「撑大窗口」而非压缩 | 无显式压缩特性（官方文档未记载） |
| 上下文隔离 | Subagents：独立上下文窗口 + 独立系统提示 + 独立权限，只回传摘要 ⭐ | 无命名隔离特性 | 官方未记载 |
| 代码库检索 | Read / Grep + MCP tool search 延迟加载工具定义 | Codebase Indexing（embedding 索引）+ `@` 引用 | 语义搜索（`#codebase`），需 workspace 索引 |
| 上下文可视化 | `/context`（占用网格 + 优化建议）⭐ | 无 | 无 |

三点观察：

**Claude Code 的差异化是"隔离 + 延迟加载"。** subagent 和 tool search 正好对应官方博客里的 isolate 和 just-in-time context 两条原则，等于把自家理论做进了产品。

**Cursor 偏"撑大窗口 + 精准引用"**，靠 Max Mode、`@` 符号、embedding 索引让用户显式控制塞什么进去（[Cursor Docs: Max Mode](https://docs.cursor.com/context/max-mode)，官方）。

**Copilot 偏"自动决策"**，agent 自己判断要什么、自动跑语义搜索，用户介入最少（[VS Code Workspace Context](https://code.visualstudio.com/docs/agents/reference/workspace-context)，官方）。

共性趋势：三家都在从「单文件全量注入」走向**渐进式披露**——条件加载、按需检索、延迟注入。原因一样，谁都逃不过 context rot。

## 反模式

- ❌ **把所有规则堆进 CLAUDE.md 或 system prompt。** 官方明确反对穷举边缘情况。堆得越多，单条规则被忽略的概率越高。该按需加载的写成 skill 或 rules。
- ❌ **靠"再强调一遍措辞"解决跑偏。** 如果 `/context` 显示 Messages 已占大半，问题不在措辞。先 `/compact` 带约束，或 `/clear` 重开。
- ❌ **裸跑 `/compact`，不带 instructions。** 摘要不知道你要保什么，硬约束经常被摘没。压缩后一定复述验证一次。
- ❌ **把上下文当垃圾桶。** 原话是 "if you treat your context like a junk drawer, the junk will influence your response"（把上下文当杂物抽屉，垃圾就会影响你的回答）——过期工具输出、陈旧历史、无关检索片段都会污染推理（[Working with Contexts](https://www.oreilly.com/radar/working-with-contexts/)，O'Reilly Radar，社区权威，2025-08）。
- ❌ **工具集臃肿。** 挂太多工具会让 agent 在选择上犹豫。不是模型笨，是上下文里的选项制造了决策噪声。官方把它列为最常见的工具失效模式。
- ❌ **主会话亲自翻日志、遍历大目录。** 一次性文本进了主上下文就出不去了，该走 subagent。
- ❌ **认为"prompt engineering 已死所以不用学"。** 官方定调是自然演进，写好指令仍是上下文工程的必要子技能。
